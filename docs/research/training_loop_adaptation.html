Short Answer

The block structure is correct. Train N epochs → adapt → repeat is the right architecture for a Kaggle-constrained, non-stationary POMDP world. The problem is not the loop shape. The problem is what the loop can observe and what it can change.
The current adaptation scope is too narrow. auto_improve.py watches 5 aggregate loss numbers and can only turn 7 scalar knobs. It is flying blind on the two signals that actually matter:
  1. IC (Spearman rank correlation) — the real predictive signal. Never measured.
  2. Per-entity-type performance — which entity types are learning vs. collapsing. Not recorded anywhere.
Changing lr and return_weight when you can't see which entities are failing is like adjusting a telescope without looking through it.

See Architecture Priority doctrine: "Model agnosticism doctrine — the test is always does this produce real edge."

The LLM path (Claude via agent/reasoning/llm_client.py) classifies the pattern and can suggest any flag combination. But it is also limited to what metrics.jsonl exposes — 5 aggregate loss values — and the same 7 scalar flag knobs. A better-informed LLM would still be blind to entity-type dynamics and IC.

The Three Fundamental Gaps

Gap 1: Observability — What the Loop Can See

Signal Currently Logged Impact of Absence
Aggregate training loss (total, return, dt, obs_type, contrastive) ✓ Yes —
Walk-forward Spearman IC ✗ Never measured We don't know if the model predicts anything real. All adaptation decisions are based on training loss proxies with unknown correlation to actual predictive edge.
Per-entity-type loss breakdown ✗ Not logged auto_improve sees GDELT dominance as "gdelt_frac too high" but can't see which specific entity types (commodity, macro, equity) are contributing to obs_type loss. Can't target adaptation at failing entity types.
Training data composition per block ✗ Not logged No record of how many observations per entity type were in each block. Can't correlate composition changes to loss changes.
Embedding drift per entity type ✗ Not logged EWC protects weights but doesn't directly measure representational drift. Can't detect if certain entity types are drifting out of the embedding space while overall EWC loss looks stable.
Gradient norm / LR schedule ~ Partial (LR logged) Grad norm not tracked — can't detect gradient explosion before it propagates to loss.

Gap 2: Adaptation Scope — What the Loop Can Change

Adaptation Lever Currently Possible Why It Matters
Scalar hyperparameters (lr, weights, temperature) ✓ Yes —
Architecture (hidden_dim, heads) via fresh_start ~ Yes, but destroys learned weights fresh_start = epoch 0 restart. 40 epochs of learning lost. Should be last resort, not a config option.
Data curriculum: entity-type weights ✗ No If GDELT entities are well-learned but commodity entities lag, we should oversample commodity in the next block. Currently impossible.
Data curriculum: recency weighting (recency_alpha) ✗ No When a regime shift is detected (fast market moves, news shock), upweight recent observations. Currently all observations equally weighted.
Observation-type gating (exclude noisy obs_types) ✗ No Some obs_types steal gradient budget without providing signal. Should be able to exclude obs_type X from one block to test if loss improves.
Prediction horizon adaptation ✗ No ListNet ranks by return over some horizon. That horizon is fixed. Short-horizon ranking may be better in volatile regimes.
Flag overrides for next block ✓ Yes (via next_config.json) —

Gap 3: Trigger Logic — When the Loop Adapts

All current triggers fire on training loss thresholds (stagnation_threshold=0.005, oscillation_cv=0.12 etc.). This means:
  • A model can have flat training loss AND declining IC — no trigger fires.
  • A model can have rising training loss AND improving IC (generalization improving while fitting gets harder) — incorrect trigger fires.
  • The system adapts by loss, not by predictive edge. This is a fundamental misalignment.
Until IC is measured, the trigger logic is necessarily loss-based. But the architecture must be designed to accept IC signals once they are available.

Concrete Build Plan (in order)

This is NOT a rewrite. It is a series of small additions that feed more information into an existing loop that already has the right shape. Each addition is independent and testable. Do not build P2 before P1 is verified.

    ic_data = json.loads(ic_path.read_text())
    ic = ic_data.get("spearman_ic", None)
    # Replace stagnation_threshold trigger:
    if ic is not None:
        if ic < 0:   DIVERGING → trigger adaptation
        if ic < 0.02: WEAK → trigger data curriculum change
        if ic > 0.05: STRONG → reduce regularization, increase lr slightly

What NOT to Build (Now)

Idea Why Defer
Neural Architecture Search (NAS) Requires fresh_start → throws away 40 epochs. Not justified until IC confirms current architecture has hit its ceiling at scale.
Experience replay buffer EWC already handles catastrophic forgetting. Add replay only if embedding drift (Step P3 metric) shows EWC is insufficient.
Dreamer world model curriculum Phase 48 target. Requires confirming Phase 40 stack is at ceiling. Not remotely justified at 339K obs.
Progressive neural networks Incompatible with current HetTGN checkpoint format. Major architectural change without evidence current arch is wrong.
Multi-task learning with new output heads We have 6 loss terms already. Adding more before IC is measured dilutes gradient budget further.

References

Source Key Takeaway How It Informs This Design
Curriculum Learning for GNNs — Kumo.ai Start with easy (well-connected, unambiguous) nodes, progress to hard. Pacing function controls transition speed. Data curriculum direction: easy = high-confidence entities (stocks with long history), hard = sparse entities (new tickers, GDELT events with few links). Entity-type weighting is a proxy for this.
TGL: Temporal GNN Training on Billion-Scale Graphs — VLDB 2022 "Random chunk scheduling" mitigates obsolete node memory with large batch sizes. Temporal-CSR structure for efficient neighbor sampling. Current trainer samples observations sequentially per block. Random chunk scheduling (shuffle blocks of temporal windows) would reduce node memory staleness — relevant when block_size is extended to 10.
Continual Graph Learning: A Survey — arXiv 2023 EWC is effective but memory-constrained. Replay-based methods (DER, ER-GNN) outperform regularization alone on tasks with large distributional shift. Progressive networks avoid forgetting but grow linearly. EWC (currently implemented) is the right first layer of protection. Replay buffer is the justified next step IF IC degrades on entity types introduced in early blocks — not before.
WMAR: World Models with Augmented Replay — arXiv 2024 DreamerV3's FIFO replay buffer is insufficient for continual RL. Distribution-matching replay (keep representative samples from each task) outperforms FIFO in non-stationary settings. When we add a replay buffer (Phase 48+), use distribution-matching not FIFO. But only after Phase 40 stack shows IC ceiling.
W&B EWC Overview — wandb.ai EWC anchors weights by Fisher information. Effective when task count is low; degrades when Fisher diagonal is stale. Our Fisher is refreshed every 5 epochs (sidecar fix in v16). This is correct — stale Fisher would make EWC a no-op over time.
