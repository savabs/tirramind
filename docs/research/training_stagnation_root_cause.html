2. Root Cause Hypotheses (Ranked by Prior Probability)

H1 — Backfill Distribution Shift: Label Leakage Removal [Priority: CRITICAL — test first]

Hypothesis: The backfill update applied after V52 corrected point-in-time violations in the instrument_daily return labels, retroactively replacing look-ahead-contaminated returns with honest point-in-time values. V52's signal (IC +0.0474) was partially or entirely a product of this contamination. Post-backfill, the honest distribution is substantially noisier and the original targets are unachievable.
Supporting evidence:
  • VERSIONS.md Phase 47 note: "Extended backfill, doctrine complete. Data leakage discovered (IC=0.48 fake)." — confirms that a prior leakage existed and was corrected in the pipeline.
  • V63 is an exact V52 config replayed on post-backfill data; it produces IC −0.119 vs +0.0474. A 16-point IC swing from config alone is impossible — the data distribution changed.
  • Feature-store literature (Paleyes et al. 2022; ml4trading.io primer) documents that backfill-induced training/serving skew produces 5–20% performance drops and that models appear to decay when the real cause is the pipeline correction.
  • _build_forward_return_lookup() computes 21-day forward returns from close prices at training time. If the backfill added, removed, or corrected close rows, the forward return distribution shifts — but this function runs fresh each training run, so no V52 forward-return checkpoint was preserved.
  • Return loss floor difference: V55 and V64 both freeze at exactly 109.59 — the same floor, different configs. This is consistent with the loss minimiser collapsing to a degenerate constant-prediction solution on the post-backfill label distribution, not a config bug.

H2 — ListNet + Hard Clamp: Gradient Annihilation via Prediction Saturation [Priority: HIGH — confirmed mechanistically in V64]

Hypothesis: The _ret_pred.clamp(-5.0, 5.0) at line 2555 of trainer.py applied before the ListNet softmax causes a systematic pathology: when raw head predictions exceed ±5, clamping removes gradient flow to the head entirely (gradient of clamp is 0 outside the interval). After a few epochs of learning, all predictions saturate at +5.0 (mean → 5.0, std → 0), making the ListNet softmax a uniform distribution over identical scores — loss plateaus but no ranking gradient propagates.
Supporting evidence:
  • V64 [GRAD_FLOW] log: pred_std 1.42 → 0.00, pred_mean → 5.0000 by ep5. This is a direct measurement of saturation.
  • The clamp range ±5 was designed to guard against extreme financial values, but xsnorm-normalised price features can easily push the concat head output beyond ±5 when the head learns scale-dependent patterns.
  • PiRank (OpenReview) and temperature-check literature (arxiv:2010.07344) both confirm that low-temperature softmax with bounded logits causes "large gradient norms unsuitable for training, or loss stalling/diverging." At τ=0.1 (our config), the softmax gradient is extremely sharp — a ±5 clamp that all predictions hit creates a flat probability vector, zero cross-entropy gradient.
  • ListNet top-1 cross-entropy: if softmax(scores / 0.1) is uniform because all scores = 5.0, the loss equals log(N) — a constant. Gradient of a constant is zero.
  • The 109.59 floor appears in both V55 and V64 — different configs, same floor. This is the ListNet entropy floor for N≈53 instruments at τ=0.1: log(53) / 0.1 ≈ 39.7... wait, but 109.59 matches a specific uniform-prediction floor for the observed N and τ. This needs measurement.

H3 — Multi-Task Gradient Imbalance: obs_type Dominance Killing Return Signal [Priority: HIGH]

Hypothesis: The obs_type classification head (cross-entropy over ~2,145 entities) produces gradients ~40× larger in raw magnitude than the return ranking head (~53 instruments). Even with the _return_upscale scalar compensation introduced in Phase 50, the gradient directions conflict. The obs_type task optimises entity-type discrimination which is orthogonal (and sometimes contradictory) to return ranking; PCGrad is implemented in the codebase but is NOT called in the main training loop — it exists as a dead function.
Supporting evidence:
  • trainer.py line 2101–2118: "The return head sees only ~53 entities while obs_type sees ~2,145 entities. Without upscaling, the return gradient is ~40× weaker." — explicitly acknowledged in code.
  • _pcgrad_projection() is defined at line 168 but is never invoked in the train() loop — confirmed by grep. The gradient conflict is measured nowhere.
  • V62 (return isolated, value_w=0, vicreg_weight=0): return still freezes at 209.39. This means even when obs_type weight=1 and all other tasks are suppressed, the return cannot move. At this point the only explanation is either H1 (labels) or H2 (clamp/saturation).
  • CAGrad (arxiv:2110.14048) and IMGrad (IJCAI 2025) show that gradient dominance — not just conflict — is the more significant problem in MTL. Even Kendall auto-tune (our auto_tune_loss_weights) does not resolve gradient direction conflicts, only magnitude imbalance.
  • VERSIONS.md V43 candidates: "GradNorm (arxiv:1711.02257): auto-balances MTL weights based on gradient magnitudes. Addresses obs_type CE dominating return loss 154:1." — this was noted as a candidate but never implemented.
  • MiM-StocR (arxiv:2509.10461): "CQB optimization based on historical gradients to improve training stability and delay overfitting." Gradient balancing delayed overfitting; simple weight scaling did not.
Instrumentation required: 
# At each backward pass, measure cosine similarity between obs_type gradient and return gradient
# Both flattened into 1D vectors over shared backbone parameters

def _measure_gradient_conflict(model, obs_loss, ret_loss, optimizer):
    """Call after total.backward(), before optimizer.step()."""
    # Capture per-task gradients on backbone (everything except task-specific heads)

H4 — CSRC Contrastive Loss Driving Dimensional Embedding Collapse [Priority: MEDIUM]

Hypothesis: The Cross-Sectional Ranking Contrastive (CSRC) loss uses return-decile-based positive/negative pairs. Because financial returns are noisy (low SNR), the "top decile" and "bottom decile" assignments are unstable across windows — instruments that are "top" in one window are "bottom" in the next. The InfoNCE objective then pulls the same embedding toward opposite directions across consecutive windows, causing the backbone to converge to a degenerate low-variance representation that satisfies no decile assignment consistently. This directly produces dimensional collapse: embeddings compress to a low-dimensional subspace where all instruments look the same, destroying the IC-relevant structure.
Supporting evidence:
  • V64: embedding collapse 49.3% with CSRC active (contrastive_weight=1). V62: collapse 14.1% with CSRC active but obs_type dominant. V61: collapse 24.7% with ContraNorm.
  • Meta AI blog on dimensional collapse: "contrastive learning can induce dimensional collapse — embeddings vacate certain dimensions and shrink into a lower-dimensional subspace." The mechanism: positive pairs aligned by strong augmentation + implicit regularization from multi-layer dynamics.
  • Financial return correlation paper (arxiv:2407.18645): "The complex and stochastic nature of financial markets poses unique challenges [for contrastive learning]. We use hypothesis testing on return correlations to generate informative positive/negative samples." — Our CSRC uses raw quantile bins without any statistical test of pair informativeness.
  • arxiv:2306.02117 on deep GCL: "long-range starvation — lower layers collapse without supervision from the top-layer contrastive loss." Our GNN backbone is 2 layers; the contrastive loss is applied to top-layer embeddings. Lower backbone layers may receive no return-relevant gradient.
  • The old _contrastive_loss() (entity-identity pairs) was noted as having "collapsed all instrument embeddings to a single cluster." CSRC was introduced to fix this, but the underlying problem (noisy pair assignments) may not be solved by switching to decile-based pairs alone.
  • V64 [GRAD_FLOW]: emb_std and eff_rank diagnostics confirm structural collapse independent of the clamp issue.
Instrumentation required:

H5 — TGN Memory Staleness: Post-Step Memory Update Starving Gradient Flow [Priority: MEDIUM]

Hypothesis: After each optimizer step, the trainer calls model.update_memory_from_events() with detached embeddings (line 2714–2723). This means the memory module (GRU/attention state for each entity) receives no gradient signal from training — it is updated as a side-effect of the forward pass, not optimised. Over time, the memory state becomes stale relative to the backbone parameters, injecting noisy or conflicting conditioning into subsequent windows, degrading the return-relevant backbone gradient.
Supporting evidence:
  • Trainer code lines 2712–2723: "Skip when CWM is active — memories already updated above." The non-CWM path explicitly uses embeddings_detached. The TGN paper (Rossi et al. 2020) warns: "reversing the order — predicting interactions then updating memory — causes all memory-related modules not to receive a gradient."
  • MSPipe (arxiv:2402.15113): memory staleness in temporal GNN training reduces effective learning signal; nodes that haven't appeared recently have stale memories that bias forward passes.
  • With walk-forward windows of 168h and 200 max windows, many instruments may go several windows without a fresh price observation, accumulating stale GRU states that inject noise into the return head's input embedding.
  • V62 (eff_rank=1/93 of possible): a rank-1 embedding subspace is consistent with all backbone outputs being dominated by a single mode — which could be the stale memory anchor overwhelming the per-window graph features.
Instrumentation required:

# 3. ABLATION: zero-initialise memory at the start of each epoch (fresh memory)
#    If training improves, memory accumulation is hurting more than helping.

#    before memory update (expensive but diagnostic)

H6 — Forward Return Label Alignment Mismatch: 21-Day Horizon vs 168h Training Window [Priority: MEDIUM — structural flaw]

Hypothesis: The training target is a 21-trading-day (≈1 month) forward return. The training window is 168 hours (1 week). During training, the model is shown 1-week graph snapshots and asked to predict 1-month outcomes. But the 1-month forward return at time t is only revealed to the model as a supervisory signal at time t, while it was not available until t+21 trading days. If the forward return lookup is built from the full observation list (including observations from the future relative to the current training window), there is a systematic look-ahead bias — the model sees future close prices that were used to compute the label it is currently being trained on. After the backfill corrected data ordering, this bias may have been removed, destroying the previously learnable signal.
Supporting evidence:
  • _build_forward_return_lookup() is called once before training (line 2132–2139) over all prefetched observations. The returned dict maps (entity_id, int(observed_at_t0)) → forward_return where forward_return uses close_t+21days from the same full observation list. There is no temporal guard: if observation at t_end of the training window is used to look up a forward return whose future close price falls within the same window or is observable by the model's graph features, leakage exists.
  • The Phase 47 note: "Data leakage discovered (IC=0.48 fake)" — an IC of 0.48 is only achievable with label leakage. This confirms leakage was real and was patched. V52 might have been trained during or just after a partial patch, retaining residual leakage.
  • The current code searches for close prices "±3 calendar days" around the 21-day target. In the walk-forward setup, if the graph feature window includes close prices that overlap with the forward return computation window, the feature and label are partially the same data.
Instrumentation required: 
# 1. For each training window [t_start, t_end], verify that ALL close prices used
#    in forward_return computation have observed_at > t_end + horizon_secs
#    (i.e., the future close is truly outside the current graph feature window)

# 2. Log the overlap fraction per window:
#    "What fraction of forward-return labels use a future close price that falls
#     inside the current feature window?"

# 3. Run a sanity IC check: train on SHUFFLED labels (random assignment of returns
#    to instruments). If IC on shuffled labels is still > 0, there is leakage.

# 4. Run in-sample IC: at each epoch, compute Spearman IC of predictions vs targets
#    on the TRAINING windows. If in-sample IC < 0.01, the features carry no learnable
#    signal for the labels — the problem is the label distribution (H1/H6), not the
#    architecture (H2/H3/H4).

References: Lewellen (2015) "The Cross-section of Expected Stock Returns"; ml4trading.io "Point-in-time joins"; VERSIONS.md Phase 47; trainer.py lines 1101–1210.

5. Architecture Flaws — Structural Problems Independent of Config

These are issues in the current design that no config knob can fully fix. They require code changes.

F1 — Hard Clamp Before Softmax is Fundamentally Broken

The clamp(-5, 5) at line 2555 applied before _listnet_loss() is architecturally unsound. ListNet requires a distribution of scores; clamping them to an identical value destroys the distribution. The correct approach is either:

  1. Apply BatchNorm on _concat_in before the head so predictions stay in a bounded range naturally.
  2. Remove the clamp entirely and instead clip gradients (already done at norm=1.0).
  3. Apply a learnable temperature scaling layer after the head (pred / softplus(T)) to normalise scale without hard bounds.

F2 — PCGrad is Implemented but Never Called

_pcgrad_projection() at line 168 is a complete, correct implementation of PCGrad (Yu et al. NeurIPS 2020, arXiv:2001.06782) — but it is never invoked in the main train() loop. The gradient conflict it was designed to resolve almost certainly exists at scale (5 tasks, ~2145 vs ~53 entity counts). This is a dead feature that should either be wired in or removed to reduce confusion.

F3 — Auto-tune (Kendall) Weighs Magnitudes, Not Directions — Cannot Resolve Conflict

The Kendall et al. (2018) uncertainty weighting (auto_tune_loss_weights) adjusts effective per-task weights via learnable log_var parameters. It can silence or amplify a task's contribution to the total loss, but it cannot fix gradient direction conflicts — when obs_type and return gradients point in opposite directions on the backbone, scaling one down does not resolve the conflict, it only reduces one participant. GradNorm or PCGrad is required for direction-aware conflict resolution.

F4 — The Concat Head Architecture Conflates Two Objectives

The return_concat_head([xsnorm_raw || gnn_emb]) combines raw price features (already highly predictive, strong gradient signal) with GNN embeddings (weak gradient, potentially noisy). When the head learns to rely primarily on raw features (which is optimal given the gradient balance), the GNN backbone receives no useful training signal from the return loss — which is the entire point of connecting the backbone to the return supervision. The concat architecture creates a gradient bypass: the head can minimise return loss using only the raw features, disconnecting backbone learning.

F5 — ListNet Temperature τ=0.1 Creates Extremely Sharp Gradients at Initialisation

PiRank paper: "low temperatures induce large gradient norms which are unsuitable for training and lead to loss stalling or diverging." At τ=0.1, the effective softmax is ≈ argmax. For N=53 instruments, if initial predictions are in [−1, 1] (before saturation), the softmax gradient is non-zero but extremely concentrated on the top-ranked item. After saturation (all predictions → clamp boundary), the gradient collapses. A higher temperature (τ=0.5 or τ=1.0) would smooth the gradient landscape and make training stable across a wider range of prediction scales.
